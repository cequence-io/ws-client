# Lean proofs of ws-client's pure parts

Machine-checked proofs, in [Lean 4](https://lean-lang.org), about four pieces of ws-client whose
correctness is a statement about every input: delimiter framing, query encoding, multipart
parameter encoding and SSE frame parsing. Where the other verification layers (see
[`docs/verification.md`](../../docs/verification.md)) check every case of a small scope or a
sample of interleavings, a theorem here holds for every input - every byte string, every
chunking, every Unicode text.

## What is proved about what

Each piece has three parts:

1. a **spec**, written from the scaladoc / the RFC alone (`Spec.lean`);
2. the **code**, in Lean, EXTRACTED from the shipped Scala (`Extracted.lean` and
   `*Extracted.lean`, generated by `sbt leanExtract` - no model in between, see below). For the
   two framers' imperative loops over arrays the proofs run over a hand-written MODEL
   (`*Model.lean`: the mutable fields a `State`, the `while` loops well-founded recursion, `Nat`
   indices) that is PROVED EQUAL to the extracted code (`*Refinement.lean`);
3. **theorems** about that code against the spec (`*Proof*.lean`, `Theorems.lean`).

**Extracted from production.** `ProductionExtract` (ws-client-verification) parses the shipped
object (`WireFormat`, `MultipartParams`, `JsonStreamFrames`) with scalameta and translates the
named members construct by construct; a construct outside its subset fails the extraction.
The generated file quotes the Scala above each definition. What the translation trusts is
named, and checked:

- the **library prelude** - the Java / Scala library calls (`String.trim`, `startsWith`,
  `indexOf`, `substring`, `replace`, `stripPrefix`, `Pattern.split`, `URLEncoder.encode`, ...),
  each written from the library's documentation (`Scala.lean`, `Java.lean`, `JavaString.lean`,
  `WireFormat/JdkUrlEncoder.lean`): the conformance target `lib` runs every one against the JVM
  on random texts and arrays (indices compared in code points);
- **the translator**: a mistranslation changes the extracted term, so either a proof about it
  breaks or the end-to-end conformance (the shipped Scala against the generated Lean, 500,000
  random cases per piece) differs. Shown on planted bugs: `value.substring(1)` changed to
  `substring(2)` in the shipped `parseFrame` fails `leanExtract --check` (the generated file
  is stale) and, once regenerated, fails the proof; a `trim` that stops at U+001F (not U+0020)
  in the prelude fails the proofs that use it;
- three modelling decisions, stated where they apply: `Json.parse` is the free constructor
  `JsValue.parsed` (the frame result is the string handed to the parser), a `try` whose
  handlers all rethrow is its body (the exception paths are outside the model), and a value
  of type `Any` is its `toString` text (the only thing `url` does with it). `Int` is Lean's
  unbounded `Int`; texts are lists of Unicode scalar values (a Java string with an unpaired
  surrogate is outside the model).

A change to one of these Scala methods regenerates the Lean (`sbt leanExtract`) and the
proofs are re-checked against the NEW code: they fail when the property no longer holds.

**The framers: extracted classes, proved equal to the models.** `ClassExtract` translates the
two `DelimiterFramer` classes the same way, mechanically: the `var` fields are a `State`, a
method that assigns a field returns `Except Failure (State x result)`, a method body is a
Lean `do` block (`let mut` locals, `s := { s with f := e }`), `throw new E(..)` is
`throw Failure.E` (the class, not the message), an array a `List UInt8`, and a `while` loop - with
its early `return` - a top-level recursive def over a step counter: `fuel` is a parameter of
every method, a loop that runs out of it fails with `Failure.outOfFuel`, and the extraction
decides nothing about termination. Two files per framer: `*Extracted.lean` (generated) and
`*Refinement.lean`, which proves, function by function, that the extracted code (`Int` indices,
fuel) equals the hand-written model the older proofs are about (`Nat` indices, well-founded
loops) - the search loops, `append`'s compaction and growth, the frame loop, `push` /
`onInput`, `finish`, and the whole stage (`byteRun_eq`, `engineRun_eq`) - for every fuel above
the bound the drivers give. `Framing/ExtractedTheorems.lean` then states every headline
theorem about the extracted code, and shows its loops never run out of that fuel
(`*_never_outOfFuel`). A bug planted in `ByteFraming`'s compaction (`scanFrom -= start - 1`) or
in the engines' framer (`scanFrom - start + 1`) fails `leanExtract --check` and, regenerated,
the refinement proofs; it made 276 of 5,000 conformance cases differ before the extraction -
the small-scope framing spec passes with it even at its audit scope, its inputs never reaching
the 256-byte buffer.

What is NOT extracted is what runs the framers: `ByteFraming.delimiter`'s `stateful` stage and
the jdk / zio-http engines' `TransformPublisher` (`push` per chunk then `finish`; `onInput`
per chunk then `onUpstreamComplete`; the first exception fails the stream) - two small
hand-written drivers (`Framing/ExtractedDrivers.lean`), each PINNED to the Scala it models:
`pins.txt` records the SHA-256 of the member's tokens (white space and comments left out) and
`sbt "leanExtract --check"` fails when it changed - re-read the driver, then renew the pin with
`sbt "leanExtract --pin"`. The link between the shipped framers and the Lean is checked end to
end by `sbt leanConformance`: every case through the Scala code - `ByteFraming.delimiter`'s
stage on four backends (neutral, Akka, fs2, ZIO: the first is the reference, fs2 and ZIO must be
identical, Akka identical or, on a failure, a prefix with the same ending - its stages fail
fast) and the engines' framer inside a real `TransformPublisher` - and through the extracted
Lean (compiled to an executable), outputs identical - 20,000 random cases per target by default
(500,000 in the audit run: long inputs, the buffer's compaction and growth, supplementary
characters).

**Java's own failures: the CHECKED extraction (framers).** The unchecked extraction above runs
on Lean's unbounded `Int` and reads an array outside its bounds as `none` - it models no `int`
that wraps and no `ArrayIndexOutOfBoundsException`. Each framer is therefore extracted a SECOND
time, in checked mode (`*Checked.lean`, the same Scala, `checked = true` in the `ClassTarget`):
every `Int` / `Long` operation is a step of `Except` (`i32` / `i64`: `intOverflow` /
`longOverflow` where Java would wrap), every array read, `Arrays.copyOf` / `copyOfRange`,
`System.arraycopy`, `new Array` and array `++` (`concatC`) is one too (`indexOutOfBounds`,
`illegalArgument`, `negativeSize` - the exceptions the JDK throws, in the order it checks them),
and an operand is computed before its use (the `&&` / `||` short-circuit is kept, so a guard
still guards its read). `Framing/ByteFramingSafety.lean` and `EngineFramerSafety.lean` prove
the checked code EQUAL to the unchecked one - lockstep, function by function - under the
invariant `Ranges` (every offset non-negative and ordered, every length at most
`Int.MaxValue - 8`) and the bound on the input (`end + chunk ≤ Int.MaxValue - 8`), and carry
it through the whole stage: `byteRunC_eq` / `engineRunC_eq` - for every input of at most
`Int.MaxValue - 8` bytes the checked run, in which every Java failure is a result, never meets
one and ends exactly as the unchecked run (`some` of it). So everything proved about the
unchecked code holds for the Java code, and the 32-bit and out-of-bounds gaps of the earlier
proofs are closed for the framers. The prelude's checked operations (`Java.readChecked`,
`copyOfRangeChecked`, `copyOfChecked`, `newArrayChecked`, `arraycopyChecked`, `concatChecked`,
`Scala.int32?` / `int64?`) are compared with the JVM by the `lib` conformance target (every
exception of the JDK, the boundaries of `int` and `long` included); its first run found the
JDK's order of checks (`copyOfRange` reports `from > to` before a bad `from`), which the
javadoc does not state. The one case that no test can reach is the sum of two array sizes
beyond `Int.MaxValue` (`concatChecked`: the allocation itself fails first); the theorems stay
far below it.

Java's `URLEncoder` is JDK code: it is modelled from its javadoc, and the conformance check runs
it against the JDK.

| Piece | Scala | Spec | Headline theorems |
|---|---|---|---|
| Delimiter framing (extracted; refinement to the models) | `ByteFraming.delimiter` (its `DelimiterFramer`), `StreamTransformers.DelimiterFramer` | split at the leftmost delimiter, then the limit (`Framing/Spec.lean`) | `framers_equivalent`, `*_eq_chunkSpec`, `*_frames_prefix`, `*_tooLong_of_reference`, `*_eq_reference_of_ne_tooLong`, `*_eq_reference_of_margin`, `*_chunking_independent`, `*_never_outOfFuel` about the extracted code (`Framing/ExtractedTheorems.lean`), from the model's (`Framing/Theorems.lean`) through `byteRun_eq` / `engineRun_eq` |
| Query encoding (extracted) | `WireFormat.encodeQueryComponent`, `WireFormat.url` | RFC 3986 2.1 / 2.3 / 3.4: percent-encoding of the UTF-8 bytes, a strict query reader | `encodeQueryComponent_eq`, `percentDecode_rfc3986Encode`, `readQuery_url` (`WireFormat/Proofs.lean`) |
| Multipart parameters (extracted) | `MultipartParams.escape` / `quoted` / `dataPartName` | WHATWG / RFC 7578 4.2 encoding, RFC 9110 tokens and quoted strings | `escape_eq`, `quoted_one_line`, `readValue_quoted`, `readValue_dataPartName`, `readQuotedRfc9110_of_no_backslash` (`Multipart/Proofs.lean`) |
| SSE frames (extracted) | `JsonStreamFrames.parseFrame` (up to the string handed to `Json.parse`) | the scaladoc's rules on the frame's lines (CRLF / CR / LF, comments, the first `data:` line, raw payloads, `[DONE]`) | `parseFrame_eq_reference` (`SseFrames/Proofs.lean`) |

In words:

- **Framing.** Both framers compute the same function of the chunks (`chunkSpec`) - proved
  through `ByteFraming`'s array compaction, growth and `scanFrom` skip, for every input shorter
  than `Int.MaxValue - 8` bytes. Against the scaladoc model they never emit a frame the model
  does not, never let an oversized frame through, agree exactly whenever they do not fail, and
  fail where the model does not only when a frame comes within `delimiter.length - 1` bytes of
  the limit; away from that edge the result does not depend on the chunking. That makes the
  two edges `FramingSmallScopeSpec` allows (and pins) the only differences there are.
- **Query encoding.** `encodeQueryComponent` is exactly RFC 3986's encoding for every text: the
  three `replace` calls on `URLEncoder`'s output never touch the inside of an escape. A strict
  RFC 3986 reader takes from `url(base, params)` exactly `base`'s own parameters followed by the
  defined `params`, whatever the keys and values contain - for any `base` without a `#`.
- **Multipart.** The encoding is the WHATWG one for every text; an encoded value contains no
  `"`, CR or LF, so a quoted value cannot end early or break the header line, and a reader takes
  back exactly the encoded value with the rest of the header untouched (a data-part name that is
  a token: the name itself).
- **SSE frames.** `parseFrame` computes exactly what the line rules say, for every frame and
  every item prefix whose field prefix (the item prefix without its trailing space) has no line
  break and does not start with `:` (true for the default `data: `). That covers the two places
  where the code departs from the line structure: the fast path that does not split a frame
  without comments or CRs, and the field search on the joined content
  (`indexOf("\n" + fieldPrefix)`), which finds the first line starting with the field and, in a
  raw payload, nothing.

## The run loop of `AsyncCall`: extracted, not transliterated (since 1.3.0)

`Calls/Model.lean` is not written by hand: `sbt leanExtract` generates it from
`ws-client-verification/.../calls/CallModel.scala` - a small Scala subset (sealed traits and
case classes, structurally recursive `def`s, `match`, `val`, `if`, `Int` arithmetic, `List` /
`Option`; anything else fails the extraction). The same Scala file is what the plan-tree spec
(`CallTreeSpec`) runs against the real `Future` interpreter and the ZIO compiler. It holds the
plans (a call as first-order data), `denote` (what a plan means, from the scaladoc of
`AsyncCall`) and `step` (the run loop of `CallFiber` as a transition function: signals, one
continuation frame per operator, a hook as a child run beside its parent, `Stop` for a
cancellation).

`Calls/Proofs.lean` proves `machine_correct`: for EVERY plan - whatever the nesting of
continuations, recoveries and hooks - the loop started on it reaches a configuration it cannot
leave, whose outcome (a value, a failure, cancelled) and hook log are `denote p`
(`machine_result` states it for any such end; `Steps.det` is why there is only one). That is
the correctness of the defunctionalized run loop - the explicit frame stack that makes the
interpreter stack-safe - against the compositional meaning.

`Calls/StackProofs.lean` proves the other half of the claim, `stack_bounded`: the loop never
holds more frames - the running fiber's and the waiting parents' together - than `depth p`,
the number of operators the plan nests on the way down to its leaf, whatever the number of
steps. A continuation (`flatMap`'s function, a recovery, a transformation) adds nothing: it
runs with only the frames below it. So a chain of `n` calls, each the continuation of the one
before (`chainRight`), and a retry chain (`retryChain`, each attempt's recovery the next
attempt) run with ONE frame for any `n` (`chainRight_constant_stack`,
`retryChain_constant_stack`), while `n` operators nested on one leaf (`chainLeft`) need `n`
(`depth_chainLeft`) - the stack-safety the interpreter's tests pin at 100,000 `flatMap`s, as a
theorem about the loop for every depth. (Plans are finite data: an infinite recursion is a
family of ever longer plans, which the bound covers one by one.)

Two checks keep the chain honest: `sbt "leanExtract --check"` fails when `Model.lean` is not the
extraction of the Scala file, and `sbt "leanExtract --cases 3000"` evaluates the generated
`denote` and `step` in the Lean interpreter on small-scope and random plans against the Scala
model. Shown to fail on planted bugs: a recovery that adds one in the machine makes
`Proofs.lean` fail to build; `+` extracted as `-` makes 71 of 500 plans differ.

What is not covered: time (a `timeout` that does not fire is its upstream), `traverse`, races
and streams, and concurrency (cancel racing a completion): the model checks and the linear
small-scope spec cover those. `Int` is Scala's 32-bit `Int` in the tests and Lean's unbounded
`Int` here - the plans use small numbers. A `Gate` in a hook (a hook is never cancelled in the
real run loop) is not excluded from the theorem, only from the tests (`hooksOk`).

## What the proofs surfaced

- A backslash in a multipart name or file name goes out as it is - as the WHATWG encoding (and
  browsers) do. An RFC 9110 `quoted-string` reader takes it as an escape: `a\b` reads as `ab`,
  and a trailing backslash escapes the closing quote, so the value never ends
  (`rfc9110_backslash_dropped`, `rfc9110_trailing_backslash`). Readers that follow the WHATWG
  convention see the name unchanged.
- A field prefix starting with `:` would let a comment line inside a raw SSE payload be taken
  for the field - excluded by the theorem's hypothesis; the default prefix is unaffected.
- A `#` in `url`'s `base` moves the appended query into the fragment - excluded by the
  theorem's hypothesis.
- Texts are Unicode scalar values: a Java string with an unpaired surrogate is outside the
  query and multipart models (and not generated by the conformance check).

## Running

```
formal/lean/check.sh         # build every proof and the conformance executable; fails on any
                             # `sorry` or an axiom beyond Lean's standard three (Axioms.lean)
sbt leanConformance          # the models against the Scala code (after check.sh)
sbt leanExtract              # rewrite every generated file: Calls/Model.lean (from CallModel.scala)
                             # and the Extracted.lean of the three pieces (from the shipped
                             # Scala) - then lake build
sbt "leanExtract --check"    # fail when a generated file is not that extraction, or a pinned
                             # driver's Scala changed (CI)
sbt "leanExtract --pin"      # renew pins.txt - only after re-reading the framer drivers
sbt "leanExtract --cases 3000"  # the generated call model evaluated against the Scala model
```

`check.sh` needs [elan](https://github.com/leanprover/elan); the toolchain is pinned in
`lean-toolchain` (Lean 4.24.0, installed by elan on first use) and the project has no
dependencies - no Mathlib. A build from scratch takes about 30 seconds on 20 cores. Build
output goes to `.lake/` (git-ignored).

Conformance knobs (system properties): `wsclient.verify.lean.cases` (per piece, default
20,000), `wsclient.verify.lean.seed` (default 1), `wsclient.verify.lean.only` (pieces whose name
contains the text: `framing`, `url`, `multipart`, `frame`, `lib`), `wsclient.verify.lean.exe` (the
executable; found from the working directory up by default).

## Conventions

- A spec is written from the scaladoc / the RFC text alone, never from the code.
- Code that is EXTRACTED (`Calls`, `WireFormat`, `Multipart`, `SseFrames`) is the Scala itself:
  `sbt leanExtract` after any change to it, `--check` fails otherwise, and the proofs are
  re-checked against the new code (the framers' refinement proofs fail when their behavior
  changes). A hand-written part that mirrors Scala (the framers' stage drivers) is pinned to it
  (`pins.txt`): a change to the Scala member changes the driver in the same commit (the pin
  and the conformance check fail otherwise). A Java / Scala library call the extraction meets
  goes through the prelude (`Scala.lean`, `Java.lean`, `JavaString.lean`,
  `WireFormat/JdkUrlEncoder.lean`), and a new prelude function gets a case in the `lib` conformance target.
- Every model and every extracted piece has a conformance target, and a conformance target is
  first shown to fail on a bug planted in the Scala code.
- A divergence from the spec is a theorem: either proved to be the only one (framing's edge),
  or shown by a computed witness (multipart's backslash).
- `Axioms.lean` lists every headline theorem; nothing may rest on `sorry`.

## Layout

```
Java.lean, JavaString.lean     Java primitives: arrays, String.replace
Scala.lean                     the other library calls the extraction maps (String, StringOps,
                               Pattern.split, a JSON value that is its text)
pins.txt                       the pinned Scala members of the framers' drivers (leanExtract --pin)
Framing/                       Spec, Scan (the search loop both framers share), SplitLemmas,
                               ByteFramingModel / Proof, EngineFramerModel / Proof,
                               ChunkSpecProofs, Theorems (about the models);
                               ByteFramingExtracted, EngineFramerExtracted (GENERATED),
                               ExtractedDrivers (the stages that run them, pinned),
                               ByteFramingRefinement, EngineFramerRefinement (extracted = model),
                               ExtractedTheorems (the headline theorems, about the shipped code);
                               ByteFramingChecked, EngineFramerChecked (GENERATED, every Java
                               failure a step of Except), ByteFramingSafety, EngineFramerSafety
                               (checked = unchecked: no overflow, no array exception)
WireFormat/                    Spec, Extracted (GENERATED), JdkUrlEncoder (the JDK's form
                               encoder, from its javadoc), Proofs
Multipart/                     Spec, Extracted (GENERATED), Proofs
SseFrames/                     Spec, Extracted (GENERATED), Proofs
Calls/                         Model (GENERATED by `sbt leanExtract`), Proofs (the loop
                               computes `denote`), StackProofs (and holds at most `depth`
                               frames)
Conformance.lean               the executable `sbt leanConformance` drives
Axioms.lean                    #print axioms of every headline theorem
```
